# **Weekly Update — April 14**

## **What we built last week and why**

Last week, we focused on turning the product from a rough planning prototype into something people could actually test end-to-end. We built out the expenses page, fixed overflowed content, and continued debugging the main user flows. We also updated the README and tested deployment-related issues so the live product would be easier for people to access and for teammates to work on. The work this week was less about adding brand-new concepts and more about making the existing MVP usable enough for outside testers.

This was important because Tripable’s value only comes through if the user can move from signup into a usable trip workspace. If the product breaks, overflows, or feels unfinished, we cannot tell whether users dislike the idea or are just blocked by the interface. The April 13–14 commits include overflow fixes, expenses page work, feature edits, testing commits, and README updates.

## **What we’re building this week and why**

This week, we are focusing on invites, notifications, and UI cleanup. The goal is to make the collaboration layer feel more real. A trip-planning product is only useful if users can bring friends in and understand what changed inside the trip.

Current user count: 17

## **Biggest blocker**

The biggest blocker is making the invite and notification flow reliable. If users cannot easily bring other people into a trip, Tripable feels like a personal planning app instead of a group planning product.
